# Implementation brief: a support agent that improves from its traces

## Goal and honest demo claim

Build on the existing fictional-shop demo. Show **two different loops**:

1. **Within a request:** a bounded LLM-driven agent decides whether to call an available information tool, inspect its result, call another tool, or finish with a recommendation/escalation. Different cases should produce different tool trajectories. It must not execute a refund, shipment, or other business action.
2. **Across requests:** failed traces and evaluator feedback trigger an improvement controller, which diagnoses a likely cause, proposes a *versioned, scoped* skill or memory-handling change, tests it, and promotes it only if independent safety/validation checks pass. This is prompt/procedural learning, **not model-weight training**. Promotion changes subsequent runs, not the run that generated the failure.

The audience should be able to follow one failure in LangSmith from customer request → selected skill and memory → LLM tool choice → tool output/error → final answer → evaluator finding → candidate change → paired re-run → promote/reject. Do not describe simulated fixtures or deterministic test-model results as live Gemini discoveries.

## Existing repo: retain, replace, and avoid

- Retain the fictional orders and authoritative policies in `agent/data/`, Gemini structured outputs in `agent/graph.py`, the read-only `get_order_details` and `search_policy` tools in `agent/tools.py`, the train/validation/heldout datasets, SQLite versioning, CLI, and optional dashboard where practical.
- Replace the fixed `plan_tools → get_order_details → search_policy → create_resolution` path with a **decision node ↔ tool node** cycle, followed by a final recommendation. `create_resolution` is currently a model wrapper, not a business action. Do not pretend it has issued a refund.
- Current `agent/memory.py` stores only globally active rules; add a separate, scoped episodic/customer-memory store and an explicit retrieval/write policy. Do not confuse the LangGraph `InMemoryStore` cache with durable memory.
- `evals/evaluators.py` currently requires all three named tools on every case: replace that metric with case-dependent tool/skill expectations and trajectory checks. Correct tool selection includes *not* calling irrelevant tools. Current policy-citation and unsupported-action checks are useful but limited.
- Keep current policy IDs/actions (`P-RETURN`, `P-DEFECT`, `P-FINAL`, `P-WRONG`, `P-DELIVERY`; `refund`, `replacement`, `warranty`, `deny`, `escalate`). Do not invent VIP exceptions, new warranty APIs, or a `create_resolution` implementation that returns “refund issued.” New fixture records are fine, but they must obey the existing policy model.
- Existing `evals/langsmith_experiments.py` only publishes holdout comparisons on request. Extend actual agent, tool, skill, and memory tracing rather than relying on unsupported pseudocode, automatic SDK magic, or unverified pricing/retention claims.

## 1. Request-time agent: real but bounded tool choice

Implement a LangGraph state containing messages, case/customer/session identifiers, current selected skill version, retrieved-memory IDs, tool observations, step count, and final structured recommendation. Use an LLM decision node with typed output (or native tool calls) to choose **one of**: call `get_order_details(order_id)`, call `search_policy(policy_ids)` or a query-based search if deliberately implemented, retrieve scoped memory, ask one clarifying question when necessary, or finish with a structured recommendation. If skill retrieval is needed, it must be an explicit observable step. A dispatcher validates allowed tool names and arguments; each tool response/error returns to the decision node. Conditional graph edges route decision → requested tool → decision, or decision → END for a recommendation/clarifying question. A clarifying question pauses the request; the next customer turn resumes the same conversation context. Do not use imaginary `StateNode` APIs or plain `add_edge(..., condition=...)`; use the LangGraph APIs actually installed in this repo.

The agent sees the customer message and intake order ID, not the gold answer. It should decide which policy to retrieve using the catalog, and can make additional calls after inspecting a result. For one case it might inspect the order then fetch P-DEFECT; another might initially fetch P-RETURN and correct itself after seeing a defect; an unresolved order can stop and escalate. Demonstrate *observed* variability, not a hard-coded tool order. If policy selection always takes two calls, be honest about that; do not force an unnecessary tool just to prove autonomy.

Operational bounds: max tool/decision steps, allowlisted read-only tools, argument validation, loop/repeat-call detection, structured tool error observations, and safe escalation on missing evidence, ambiguous ID, unknown policy, exhaustion, or model failure. Require order evidence and applicable **current** policy text before a non-escalation decision; cite only retrieved policy IDs. These are hard safety constraints, not mutable skills. No successful outcome can be inferred merely because a reply was drafted.

## 2. Skill: a procedure, not a renamed tool

Create a **real, versioned text skill at `skills.md`** (or `skills/support-resolution/SKILL.md` if the loader explicitly supports that layout; retain a discoverable file and show its contents). It is a procedural instruction the agent loads for support-resolution cases, not an `OrderLookup` function or a thin template saying “call get_order_details.” Do not rely on a filename to inject it magically: implement and trace the skill loader/selector, expose `skill_id`, version/hash, and loaded content in traces and artifacts. If only one skill exists, the selector can be a transparent support-domain check; do not claim sophisticated skill routing.

Initial `skills.md` should be short and plausible, with these sections:

- **When to use:** deciding a fictional-shop support recommendation from a customer request; no execution authority.
- **Procedure:** identify the customer's issue and intake order ID; inspect authoritative order facts and relevant policy; distinguish request from eligibility; choose exactly one action; cite the policy used; give a concise empathetic reply and next step; escalate if evidence is insufficient.
- **Examples / precedence:** apply specific defect and wrong-item rules before general return rules; final sale blocks preference returns, not defect or wrong-item rights; handle time windows and stock status based on the retrieved policy. The *initial* skill may intentionally omit one of these precedence clarifications while still being plausible (see scenarios below).
- **Evidence & trust:** current policy and order facts outrank the customer’s requested action, historical case notes, and model intuition. Historical notes are precedents, not permissions.
- **Limits:** never claim an action already happened; no refund/shipment side effects; unclear facts → ask for clarification or escalate within the supported output contract.

**Demonstration gap A — missing instruction:** start with a reasonable skill that says “check the relevant returns policy” but fails to state that a confirmed defect on a final-sale item follows P-DEFECT rather than P-FINAL. Use an existing training/validation pair such as C-14 (training) and C-07 (validation), plus an untouched held-out variant. The agent may choose P-FINAL only and deny or offer the wrong remedy. The proposed patch should add a *general* precedence rule grounded in policy, not a case-ID-specific answer. Since model behavior is stochastic, only claim this was the cause when the trace actually shows that error; otherwise select a genuine observed failure or show the fixture as an illustrative scenario.

**Demonstration gap B — misleading instruction:** provide an *isolated candidate or fixture* skill version containing a plausible but wrong shortcut such as “if defective, prioritize the customer's requested refund.” On day 75 (C-03), current P-DEFECT specifies warranty instead. Its policy review/regression suite should reject it. Do not ship this as the active production instruction and do not hard-code a magical word detector as the entire safeguard; check whether its recommendations contradict actual policy facts.

A learned update should contain `target=skill`, old/new file content or a small patch, diagnosis, evidence trace IDs, source policy citations, version/hash, evaluator results, and rollback pointer. Require a candidate to improve at least one validation failure, introduce no new validation regressions or policy violations, and pass a specific safety suite. No unconstrained autonomous edits to authoritative policies, code, tool implementations, or evaluator labels.

## 3. Memory: what is saved, when, and why retrieval can mislead

Distinguish three layers:

| Layer | Scope and lifetime | Contents | How used |
|---|---|---|---|
| Thread state | One conversation | recent user/assistant turns, current tool observations, unresolved question | loaded during that thread only; not presented as a durable lesson |
| Customer/case memory | durable SQLite, keyed by fictional customer/order and case | a *minimal* factual case summary and verified outcome with provenance | exact customer/order lookup for a later related conversation; only relevant records injected |
| Procedural memory | durable, versioned SQLite + file/artifact | approved skill/rules and memory-use rules, their validation and rollback metadata | active version loaded on new agent runs; not unreviewed conversation text |

Do **not** save raw entire conversations, gold labels, payment details, unsupported VIP status, or the agent’s unverified recommendation as a verified outcome. Model output, customer claim, tool-verified fact, and confirmed human outcome must have different `source_type` and `verification_status` fields. A draft recommendation may be recorded for tracing but must not masquerade as an executed resolution.

Suggested case record: `memory_id`, `customer_id` (fictional), `order_id`, `issue_type`, `issue_summary`, `policy_ids`, `policy_version_or_hash`, `recommendation`, `outcome_status` (`proposed`/`human_confirmed`/`unknown`), `source_type`, `source_trace_id`, `created_at`, `updated_at`, `expires_at`, `supersedes_id`, `trust_level`. Avoid arbitrary customer labels. Save a case summary **after** the run is assessed/closed; mark recommendation-only cases `proposed`. Only human-confirmed outcomes become verified precedent. Promotion of a general procedural lesson follows the validation gate, not every conversation.

Retrieval: start with exact fictional customer/order scope plus issue relevance, not a global bag of similar anecdotes; cap results and age, surface IDs, source and policy version, and flag stale/contradictory entries. Retrieval is optional per request: if this is a first-time order with sufficient current facts, the trace should show no memory read or an empty result. Memory never overrides current policy/order facts. Expose a typed `retrieve_case_memory` read and a controller-gated `write_case_memory` path; the request agent should not silently promote its own proposed outcomes. Provide a correction/tombstone path with provenance and a way to disable a bad record without deleting the audit trail.

**Demonstration gap C — plausible stale memory:** use a clearly labeled seeded *fictional* prior case for the same customer/issue, e.g. a previous defect reported on day 8 when replacement stock was unavailable, for which a refund was correctly recommended under P-DEFECT. A new conversation about a different order at day 75 has stock available; it requires warranty, not the old refund recommendation. Initially a deliberately deficient memory-use rule might summarize this as “we refunded this customer's defect before, so refund again.” The current order and current policy must win. Show in the trace whether memory was retrieved, which ID/version, whether the agent actually relied on it, and what current fact it missed. A candidate fix should demote the old outcome to contextual history, require fresh order and policy evidence, and/or change retrieval to filter by eligibility conditions. The seed is test data, not a real customer fact or malicious prompt inserted into trusted policy text.

**Demonstration gap D — contaminated write (optional):** after a request the assistant *proposes* a refund, an unsafe memory writer labels it `human_confirmed`; the next run wrongly treats it as precedent. The fix is to separate proposed versus verified outcomes and gate verified writes on explicit confirmation. For a short demo, prioritize gap A plus C and leave D as a regression test.

## 4. Traces and root-cause diagnosis in LangSmith

When credentials are available, trace the parent request with nested, distinguishable spans for `skill.select/load`, `memory.retrieve`, each `agent.decide` (including selected action, not private reasoning), each tool call/result/error, `memory.write` (if any), `resolution`, evaluator, diagnosis, candidate evaluation, and promotion decision. Attach `case_id`, `conversation_id`, `agent_version`, `skill_version/hash`, `memory_snapshot_id`, `policy_version/hash`, and experiment label. Include selected IDs and concise sanitized observations; do not log real PII or API keys. Preserve an offline JSON trajectory if LangSmith is unavailable. Link local reports to LangSmith run/experiment URLs or IDs when available. Verify the installed LangSmith API rather than copying the old brief's `wrap_openai(OpenAI())` snippet (this repo uses Gemini).

A diagnosis must be evidence-based and categorized, not merely “the agent got it wrong”:

| Failure category | Trace evidence to show | Candidate target |
|---|---|---|
| Tool-selection / execution | missing or irrelevant call, wrong policy ID, malformed args, tool error, repeated call | decision guidance or tool error handling; fix a broken tool only if trace proves it |
| Skill / instruction | loaded skill omitted precedence or gave conflicting guidance despite correct tool facts | targeted `skills.md` patch |
| Memory retrieval / use | stale record ID loaded, current facts disagreed, response followed old recommendation | retrieval/write/trust rule or tombstone; not current policy |
| Answer synthesis | correct facts retrieved, wrong action/citation or falsely claimed completion | response guidance and output validator |

The controller can use Gemini to propose a structured diagnosis and candidate patch, but diagnostics must cite trace step IDs, retrieved policy text, and a reproducible failure; a human can inspect and override. Only update allowlisted skill text or memory handling rules/records. Never let an untrusted customer message instruct the controller to rewrite the skill or memory.

Make the learning trigger explicit: after an externally assessed run (local evaluator or trusted reviewer feedback) is marked failed, queue a single improvement job with its trace ID and version snapshot. The controller automatically diagnoses, proposes **one** scoped candidate, evaluates it, and either atomically promotes a safe passing change or records a rejection. Avoid recursive self-training on its own unverified answers and avoid launching multiple jobs for the same failure. A CLI may trigger/replay this same job for the presentation, but the improvement must not depend on the presenter manually editing `skills.md`. Log the trigger, candidate patch, evidence and resulting active version. Human approval remains necessary for permission/policy changes (normally disallowed here).

**Optional tool/execution failure to contrast with skill/memory failures:** use a fictional case with a missing or mistyped intake order ID. Trace a failed `get_order_details` call and an agent that repeatedly retries the same invalid argument or answers without order evidence. The fix is bounded error handling/clarification or escalation, not a refund-rule edit. Test that the corrected agent does not loop and that it never fabricates order facts. This is an error-mode fixture; do not claim Gemini made that mistake unless the actual trace shows it.

## 5. Evaluation, isolation, and promotion

Retain train → validation → untouched heldout separation. Training failures and their traces may inform diagnosis. Validation is used for candidate selection and gate decisions; heldout is read **once for the final comparison**, not fed into reflection, repeated patch attempts, or promotion. If heldout reveals a regression, report it and roll back/prepare a new cycle without calling that set untouched again. Add a small safety/regression suite independent of the source case and memory scenario, with matched pre-seeded memory snapshots for baseline and candidate.

Use *paired* baseline/candidate runs with identical case inputs, order/policy fixtures, memory snapshots (except the specifically tested memory patch), model settings, and skill versions captured in metadata. Scores include: action correctness, policy eligibility/citations grounded in retrieved policy, relevant tool use and order lookup, safe stop on missing evidence, stale-memory reliance, false completed-action claims, step count/cost. A tool call made for the wrong reason should not pass simply because a set of names is present. Critical policy violations or invented completed actions fail the gate regardless of aggregate score. Keep deterministic fake-model tests separate from claims about live Gemini; real model outcomes may vary, so report actual scores and traces without manufacturing failures.

Candidate gate: supported by current policy, fixes at least one observed validation failure, zero new critical policy/safety failures and zero previously passing validation cases regressed. Store rejected candidates too. Promote atomically with active version and rollback pointer; new runs load the new version. Human approval is required if a proposed change would broaden permissions or business policy; those changes should normally be disallowed in this demo. The bad update remains inspectable, but inactive.

## 6. Customer chat UI: thin front end, real graph behind it

Add a simple customer-facing Streamlit chat (reuse the optional dashboard dependency), separate from the operator/evaluation dashboard. The customer sees their messages and a helpful response, **not** internal traces, memory contents, expected answers, candidate skills, or promotion controls. The operator view can expose the trace link, skill/memory versions and evaluation artifacts. Keep the UI intentionally small; do not add authentication, payment processing, order changes, or a full commerce backend just for this demo. Use fictional customers and orders only.

**Conversation contract:** provide a `handle_message(session_id, customer_id_or_demo_identity, message, optional_order_id)` entrypoint backed by the agent graph. Maintain thread state (`messages`, pending order-ID request, known order ID, last trace ID) per session. The first customer message may omit an order ID; in that case the assistant politely asks for it and remembers the original issue. On the next turn, extract/validate an ID of the repo's `O-###` shape (or take it from a clearly labeled order-ID field); if it is missing or malformed, ask again without guessing. Once present, check it against `get_order_details`; an unknown ID gets a clarification or safe escalation. If an order exists but material issue details are still missing, the agent may ask a concise follow-up and resume with the customer's answer instead of guessing. The assistant should not claim ownership verification—there is no real authentication in this demo. For repeat turns with a known ID, avoid asking again unless the customer switches orders or the ID is ambiguous; keep the issue context and let the agent choose information tools. When the request has enough intake information, invoke the **same** agent graph as CLI/evaluation, not a duplicated UI-specific policy flow. This pre-agent intake guard is allowed; it is not evidence of autonomous tool choice.

Return a typed result such as `assistant_message`, `status` (`needs_order_id`, `answered`, `escalated`, `error`), `session_id`, `trace_id`, and optional *recommended* action. Do not return “refund processed.” Distinguish the visible assistant reply from internal run metadata. An interrupted or failed tool call yields a safe customer message and an inspectable operator trace, never raw stack traces in the customer chat. Prevent Streamlit rerenders from submitting the same customer turn twice; use session-scoped IDs and an idempotent turn ID. Prevent one customer's conversation from leaking into another's thread or durable memory.

**Persistence distinction:** Streamlit session state can hold one browser session for the demo; use an explicit thread/checkpoint store if reload/restart continuity is promised. Customer/case memory in SQLite is separately persisted and deliberately retrieved on later conversations as described above. Show one two-turn missing-ID conversation and one later conversation that retrieves a scoped prior memory. Seed fixtures/reset controls belong to the operator demo view, not the customer's chat.

**Tests:** missing-ID → ask → valid ID → original issue resolved; malformed and unknown IDs; follow-up without repeating intake; changed order ID; two concurrent sessions isolated; refresh/re-render does not duplicate the agent run; graph output and CLI case path obey the same policy contract. Verify one submitted UI turn has a corresponding LangSmith trace (when configured), and that customer messages do not expose internal skill/memory artifacts.

## 7. Concrete demo trajectory (20 minutes)

Prepare a saved real Gemini run and LangSmith URLs ahead of time. The live execution can replay a fresh case, but saved runs are the fallback; do not present fake-model unit tests as model results.

1. **2 min — customer chat:** enter a request without an order ID, see the assistant ask for one, supply it, and follow the resulting request into a LangSmith trace. Show that intake is deterministic while the graph chooses subsequent information tools. Contrast the graph with the old fixed path.
2. **4 min — skill gap:** open `skills.md` v1 and a trace of a final-sale defect mishandled through P-FINAL; show order facts, loaded skill version, policy lookup and incorrect final action. If the live model didn't make that mistake, use another actual failed trace and say why.
3. **3 min — diagnosis:** open the LangSmith trace and evaluator feedback; pinpoint the missing precedence instruction rather than calling every error a prompt failure.
4. **3 min — candidate learning:** show controller's proposed minimal skill diff, authoritative P-FINAL/P-DEFECT excerpts, validation comparison, and decision to promote or reject. Re-run a similar, not identical case with v2 and trace the changed behavior.
5. **4 min — memory across conversations:** run a seeded prior case and a new case for the same fictional customer; show saved memory ID, what was retrieved, why prior refund is not transferable, candidate retrieval/trust fix and a paired re-run. Use isolated snapshots so earlier demonstrations cannot contaminate the next one.
6. **2 min — safety:** show rejected misleading “refund all defects” skill or unsafe memory-write candidate and remaining failures/regressions. Demonstrate rollback if a previously promoted version exists.
7. **2 min — limitations:** fictional data, recommendations only, small tests, narrow deterministic evaluators, human oversight, no weights trained, no guarantee every candidate improves.

Provide CLI commands within the existing `demo.py` (or small documented additions) for `case`, baseline experiment, `diagnose`, `propose`, `validate`, `promote`/`reject`, `compare`, `safeguard`, and `rollback`, with `--run-dir`, `--skill-version`, and `--memory-snapshot` where useful. Commands in docs must exist and be tested; don't invent `run_agent.py`/`evaluate_agent.py` unless actually added. Provide a documented command to launch the customer chat using the optional Streamlit extra. The existing dashboard remains an operator artifact viewer: show per-case trajectory, skill/memory versions and IDs, diff, evaluator evidence and promotion status; it is not a substitute for LangSmith traces.

## Acceptance tests / deliverables

- At least two requests produce different **observed** tool choices; unsupported tool name, bad arguments, repeated calls and step exhaustion safely stop or escalate. All information tools are read-only; no output asserts a business action already happened.
- `skills.md` v1 and v2 are loadable, traceable, diffable, and reversible; a test proves a policy-grounded general rule fixes the intended case without hardcoding an answer to that case ID.
- A two-conversation fixture demonstrates a memory write/retrieval across independent requests. A proposed outcome remains unverified; stale or conflicting history cannot outrank current policy. Retrieval and any write appear as trace spans with IDs.
- LangSmith parent runs expose decisions, skill/memory versions, tool observations and evaluator outcomes. Local saved traces/reports work without LangSmith. A failure can be classified using actual evidence in the trace.
- Validation gate catches skill/memory regressions; heldout remains unseen until final report. Promotion and rollback persist across process restarts. Tests cover acceptance, rejection and rollback with fake model; separately document results from real Gemini runs.
- Update `README.md` and `DEMO_GUIDE.md` with verified setup/commands, limitations, and the exact saved-run fallback. Keep `uv`/`pyproject.toml`/`uv.lock` as the dependency workflow.

**Success condition:** after viewing one LangSmith failure, an audience member can say precisely whether it came from tool choice, missing/conflicting skill instruction, stale/incorrect memory, or final-answer synthesis; identify the trace evidence; see the smallest candidate correction; and see independent evidence that the correction helped without silently changing policy or executing a real-world action.
